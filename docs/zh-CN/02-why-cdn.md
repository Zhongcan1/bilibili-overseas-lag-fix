# 02 · 为什么只有冷门视频转圈：海外 CDN 冷缓存与实测数据

**简体中文** · [English](../en/02-why-cdn.md) · [← 返回首页](../../README.md)

> **一句话**：热门视频命中海外边缘节点的缓存，所以很快。冷门视频在海外边缘上没有缓存，每段数据都要回中国大陆的源站取，而 B 站网页播放器每段只开 1 条连接，也不会因为“慢”就换节点，于是只能转圈。荷兰案例的 3 个冷门视频都是这个规律：**B 站分配的海外节点远低于码率，“大陆节点 + 并行”稳定在 24–26 Mbps。**

## 1. 原理

```
热门视频：你 ──几 ms──▶ 本地海外边缘（已有缓存）────────────────▶ 秒开
冷门视频：你 ──几 ms──▶ 本地海外边缘（没有缓存）──200–330 ms × 每个请求──▶ 中国大陆源站
```

- **分段下载**：B 站网页播放器用 DASH，视频被切成很多小段，每段用 HTTP Range 请求下载。页面会拿到一个“主地址”和一个“备用地址”。在荷兰案例里，主地址是 Akamai（`upos-hz-mirrorakam.akamaized.net`），备用地址是 `upos-sz-mirrorcosov.bilivideo.com`（海外节点）。
- **单连接、不因为慢而换**：播放器每段只开 1 条连接（[BTR README](https://github.com/MrTangLuyao/Bilibili-thread-ripper/blob/0302b345cdfe367ac599b52dc6874e3f7967e220/README.md?plain=1#L112)），只在出错或超时时才换节点，不会因为速度慢而换（[realzza 的测量文档](https://github.com/realzza/bilibili-accelerator/blob/main/docs/vod-routing.md)）。
- **冷数据要回源**：边缘节点没有缓存时，每个请求都要先去源站取。实测首字节时间（TTFB）约 2 秒，吞吐也很低。
- **为什么“并行”有用**：瓶颈在“每个请求在服务端回源”这一步，几个请求同时回源，总速度就上去了。热门视频上，并行几乎没有提升（见 §4）。这说明收益集中在冷数据上。
- **为什么“大陆节点”有用**（推断）：内容本来就存在大陆，大陆节点虽然离你远（往返 200–330 ms），回源这一段却短得多。
- **为什么抖音不卡**（推断）：抖音网页的视频域名 `v3-web.douyinvod.com` 也落在同一家阿里云的荷兰边缘节点上（从响应头可以看出）。但抖音视频短、热门、码率低，还会连续预加载，几乎总能命中缓存。差别在内容热度，不在线路。

## 3. 第 3 轮：登录后 1080P60（最贴近日常观看）

单连接 = 一条连接下载 2 MB，也就是 B 站原生播放器的方式。8 路并行 = 把同样多的字节拆成 8 段同时下载，也就是 BTR 这类脚本的方式。“÷码率”是速度除以 3.48 Mbps，✅ 表示 ≥ 1.5。

| 节点 | 类型 | 单连接 Mbps | ÷码率 | 8 路并行 Mbps | ÷码率 | 单连接 TTFB |
|---|---|---:|---:|---:|---:|---:|
| `upos-hz-mirrorakam.akamaized.net` | **B 站分配·主**（Akamai） | 0.4（超时） | 0.11 | 0.7 | 0.20 | 2088 ms |
| `upos-sz-mirrorcosov` | **B 站分配·备**（海外） | 0.4（超时） | 0.11 | 0.9 | 0.26 | 502 ms |
| `upos-sz-mirroraliov` | 海外 | 1.0（超时） | 0.29 | 3.3 | 0.95 | 920 ms |
| `cn-hk-eq-01-01` | 香港 | 1.0（超时） | 0.29 | 4.5 | 1.29 | 774 ms |
| `upos-sz-mirrorali` | 大陆 | 6.9 | ✅ 1.98 | 11.0 | ✅ 3.16 | 1180 ms |
| `upos-sz-mirrorhw` | 大陆 | 6.0 | ✅ 1.72 | **26.3** | ✅ 7.56 | 1206 ms |
| `upos-sz-mirror08c` | 大陆 | **18.1** | ✅ 5.20 | 6.0 | ✅ 1.72 | 606 ms |
| `upos-sz-mirrorcos` | 大陆 | 2.3 | 0.66 | 7.6 | ✅ 2.18 | 1444 ms |
| `upos-sz-mirrorbd` | 大陆 | 4.6 | 1.32 | **25.5** | ✅ 7.33 | 1711 ms |
| `upos-sz-estgoss` | 大陆 | 3.9 | 1.12 | 9.7 | ✅ 2.79 | 2802 ms |

**怎么读这张表**

1. **B 站分配的两个海外节点在冷门内容上，单连接不到码率的 1/5（约 0.11 倍），8 路并行也不到 0.3 倍**，所以必然卡。Akamai 的首字节时间要等 2.1 秒。
2. **有几个大陆节点单连接就够**：08c（5.2 倍）、ali（2.0 倍）、hw（1.7 倍）。
3. **“大陆 + 并行”余量最大**：hw 26.3、bd 25.5 Mbps，约为通过线 5.2 Mbps 的 5 倍。
4. **只靠海外节点，并行也不够**：海外最好的是香港的 4.5 Mbps 并行，低于 5.2。
5. 按 `cdn-bench.js` 的规则，这一轮的结论提示是：“换个节点、单连接就够”。所以对这个视频来说，轻量的单连接换源脚本（realzza）可能就够了，BTR 也可以。但第 2 轮里 ali 完全超时，**单个节点并不可靠**（见 §5）。

## 5. 三个冷门视频的共同规律

| | 第 1 轮（480P） | 第 2 轮（360P） | 第 3 轮（1080P60） |
|---|---|---|---|
| 分配主节点 Akamai：单连接 / TTFB | 3.6 Mbps / 2119 ms | 5.7 Mbps / 1792 ms | 0.4 Mbps（超时）/ 2088 ms |
| 分配备节点 cosov：单连接 | 超时 | 2.8 Mbps | 0.4 Mbps（超时） |
| 最佳大陆单连接 | 08c 8.4 | 08c 7.6 | 08c 18.1 |
| 最佳大陆 8 路并行 | hw 26.4 | hw 24.0 | hw 26.3 |
| 最佳海外 8 路并行（含分配节点） | aliov 3.5 | Akamai 7.7 | 香港 4.5 |

1. **热门不卡，冷门卡**：同一个 Akamai 节点，热门视频 63 Mbps；冷门视频 0.4–5.7 Mbps，首字节还要等约 2 秒。
2. **“大陆 + 并行”很稳定**：3 个视频、3 种清晰度，最好的都在 24–26 Mbps。
3. **单个大陆节点不稳定**：ali 三轮分别是 5.3、超时、6.9 Mbps。只钉一个大陆节点的方案（CDN 切换器一类）有风险；“多节点 + 测速 + 失败降级”的设计更适合。
4. **对 Akamai 冷数据并行，反而更糟**（0.5–0.7 Mbps，还有超时）。不要对 Akamai 用 aria2c `-x16` 之类的多连接下载。
5. **并行的收益集中在冷数据上**：热门视频上 hw、08c、bd 的并行和单连接差不多。

## 6. 其它网络观测（同一天、同一台电脑）

- **往返时延**：海外边缘 5–12 ms（Akamai 荷兰本地节点、cosov 走 EdgeOne、aliov 是阿里云荷兰节点）；大陆 upos 节点 215–330 ms（经欧洲的交换中心，再转入中国运营商的国际骨干网）；B 站香港节点约 200 ms，而且有丢包。
- **协议**：Akamai 和 estgoss 只协商到 HTTP/1.1（Akamai 另外通告了 HTTP/3），其它 upos 节点都是 HTTP/2。
- **共享 IP**：hw、08c、08h、hwo1、08ct 解析到同一组华为 GSLB 地址，cos 和 coso1 也共用 IP。所以它们**不是彼此独立的线路**，Chrome 还可能把同 IP、同证书的主机合并到一条连接上。

## 7. 为什么这些数字只能当方向参考

- **单次样本**：每个节点每轮只测一次，也没有覆盖不同时段。国内晚高峰是北京时间 19–23 点，相当于中欧夏令时 13–17 点、冬令时 12–16 点，美国东部夏令时 7–11 点。[realzza 的数据](https://github.com/realzza/bilibili-accelerator/blob/main/docs/vod-routing.md)里，同一个冷文件在国内晚上和凌晨能差 10 倍。
- **HTTP/2 复用**：浏览器对同一个大陆主机发 8 路并行，其实是一条 TCP 连接上的 8 个流。所以几个节点的并行速度**不能简单相加**。用 curl 开多连接测出来的数字会更乐观。
- **TCP 慢启动**：往返 200–330 ms 时，2 MB 的单连接样本可能还没走出慢启动，大陆单连接的数字可能偏低。可以把 `cdn-bench.js` 的 `SINGLE_MB` 改成 8 再测。
- **测过就热了**：只有第一次读某段字节才算“冷”。复测要换视频或换区间（`cdn-bench.js` 每次都会随机错开区间）。
- **地区差异**：别的国家可能被分配到不同的节点。[realzza 的文档](https://github.com/realzza/bilibili-accelerator/blob/main/docs/vod-routing.md)也提醒，欧洲和美国西岸的分配可能不同。

## 8. 自己测一次

1. 先读 [`tools/README.md`](../../tools/README.md) 和 [`tools/cdn-bench.js`](../../tools/cdn-bench.js)（只读，不带 Cookie，只连 B 站视频 CDN）。
2. 停用所有 B 站加速脚本，关掉 VPN、WARP 和代理；笔记本插上电。
3. **登录**，把清晰度切到你平时看的那档。打开一个**你从没看过**的低播放量长视频，按 F5 刷新，出画面后立刻暂停。
4. F12 → Console，粘贴运行，等 1–6 分钟。
5. 看最后的「结论提示」：

| 结论提示 | 含义 | 下一步 |
|---|---|---|
| 分配的主节点单连接 ≥ 1.5 倍码率 | 这个视频对你来说是“热”的，CDN 不是问题 | 回到 [01 · 诊断](01-diagnosis.md)，不用装加速脚本 |
| 换个节点，单连接就 ≥ 1.5 倍码率 | 换源就够 | 轻量的 realzza 可能就够，BTR 也可以（[04](04-alternatives.md)、[05](05-safe-install.md)） |
| “大陆 + 并行” ≥ 1.5 倍码率 | 需要并行 | BTR 钉版本（[05](05-safe-install.md)），或 MBGTEB 的 Thread Ripper 模块 |
| 只有“海外 + 并行” ≥ 1.5 倍码率 | 需要并行，但大陆线路不够 | BTR 钉版本的海外模式，或 MBGTEB 的 Thread Ripper 模块 |
| 全都不到 1.5 倍码率 | 加速脚本也救不了 | 降低清晰度、用 HEVC / AV1、离线缓存 |

保存结果：在控制台输入 `copy(JSON.stringify(__cdnBench))`。结果里没有签名地址，也没有 IP。
